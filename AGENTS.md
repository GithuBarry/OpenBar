# Agent access: MCP and WebMCP

OpenBar exposes native MCP and WebMCP tools for research projects. Start with `get_project_state`. Tool descriptions and schemas define each operation. Project state lists instructions and skills for reading when relevant. `/agents` covers connection setup, `/llms-deployment.txt` covers deployment and transports, and `/llms.txt` is an optional index.

After changing application code or styles, rebuild and restart the running local OpenBar service, then verify the live app before reporting completion.

## Agent inbox and response prefixes

At the start of each OpenBar agent session, including one without earlier chat context, call `check_inbox` after `get_project_state`. Treat "tick", "check updates", "check inbox", and "sync" as requests to call `check_inbox`. When sync also names a Git or Overleaf action, check the inbox first, then perform the requested synchronization. Saved mindmap `@agent` and `@stat` mentions are requests whose original wording stays in the paper, map, or collapsed Notes. `@stat` displays as "agent STAT" and fast tracks the request ahead of ordinary mentions, using the same reply and acknowledgement flow. After answering, remove the mention from the visible copy and write an ordinary card that a reader can understand on its own. Match neighboring cards and keep useful existing wording. Rephrase or omit the visible question, or use a concise Q&A when it clarifies the answer. When replacing a map-owned ask, preserve the original once in `caption` alongside existing Notes in the same patch. OpenBar tool results may start with pending notifications. Read the linked card and its current context, call `claim_inbox` only for the request(s) you are immediately starting to work on (or `{ project, all: true }` only when immediately working on all pending requests in that project; claims turn `@agent` into a spinning indicator for 30 minutes before reverting automatically), reply there within the user's instructions, then call `acknowledge_inbox` with the exact notification IDs. Repeated IDs represent the same request. Editing the request text produces a new ID. Acknowledgement records handling, while paper TODO completion follows the research decision. The Tools panel lets humans inspect, handle, and reopen notifications. Prefixes arrive with the next OpenBar tool call. MCP Events clients (such as OpenCode 2.3+ with `experimental.mcp_events` and `"protocol": "auto"`) can subscribe to `openbar.inbox.mention` (for `@agent`/`@stat` mentions) and `openbar.git.conflict` (for Git sync and saved-file mindmap/paper conflicts) with `{ project: "<slug>" }`, `{ projects: [...] }`, or `{}` (all accessible projects), using `once: false` for continuous wakes, then call `check_inbox` after subscribing and on each mention wake. When a conflict alert or `openbar.git.conflict` event arrives, inspect the conflict and resolve it if confident nothing (including unsaved human edits) will be lost; otherwise summarize what conflicted and wait for the human to tell you what to do.

# OpenBar product invariants

OpenBar edits an Overleaf-style research-paper repository.

- Paper sections are derived from current LaTeX headings and include order. Section addresses are revision-local. Keep manuscripts free of OB-SECTION and section OB-EDIT comments and use current hashes or revisions for edits.
- Paper owns the scientific argument, every TODO, comments, and intentionally incomplete structures (tables, figures, plots, `\obmarker` cells).
- Manuscript `.tex` prose must read for an external peer reviewer—never as an internal lab log. Never put internal iteration/version labels for your own method or runs (`v1`, `v2`, `v3`, `trace-repaired`, `wave`, `phase`, `smoke`, `confirmatory`), local harness script paths or JSON/SQLite filenames, or execution bookkeeping (`0 technical failures`, `cells`) into `.tex` prose, headings, captions, or tables. Present one coherent final design and frame variant comparisons as named component ablations; keep execution provenance and debugging history in collapsed mindmap Notes or wiki pages. (External third-party benchmark/model/API versions such as `AgentDojo v1.2.2` are fine.)
- Work-in-progress papers visibly carry their unfinished reasoning throughout the manuscript: TODOs, questions, notes, planned comparisons, partial tables, and local result holes. Preserve this working-paper state until evidence or an explicit research decision resolves each open point.
- Begin with the intended full paper skeleton and retain its eventual scope while evidence fills it in. Planned sections, argument steps, comparison axes, tables, and figures can remain partly empty. Completion can decrease when the research changes or expands, and the manuscript should expose the newly opened work.
- Deliver useful structure early and refine it as work progresses. Choose the presentation that makes the project's direction, planned scope, known results, and remaining work quickest to understand.

  Mindmap structure: Use meaningful branching relationships in the project's own terms. Write concise prose cards, use child cards for distinct topics, and put supporting detail in collapsed Notes. Definitions, explanations, and conclusions belong in prose cards or Notes. Keep branches scannable with progressive depth: group crowded sibling lists under intermediate headline / evidence / diagnostics cards, keep shallow headline cards brief with wide data tables nested deeper, patch or move superseded prototypes/smoke runs into an Archive branch (`presentation: { shape: "archive", defaultCollapsed: true }`), and fold answered `@agent`/`@stat` threads into the owning card rather than leaving top-level Q&A siblings. Mention related cards inline with `[[card-id]]` or `[[card-id|Label]]`, and wrap optional Markdown hover details in `((detail))` to render an `(i)` icon with a mouseover tooltip.

  State the takeaway in one sentence a new reader can understand. Quantify changes against a named baseline on a stated sample. Use prose for a simple fact, a table for exact comparisons, or a labeled chart for a pattern. Keep headings short. Give shared units or denominators once per column, and split long labels across lines with `<br>` in Markdown tables. When stacking multiple metrics in a Markdown table row, use explicit `<br>` breaks in both the label cell and every value cell so numbers stay line-aligned across columns (avoid `/` lists that wrap unpredictably into 2 vs. 3 lines), or split metrics into separate rows/columns. Wrap optional Markdown hover details in `((detail))` to render an `(i)` mouseover tooltip. Show uncertainty and evidence gaps beside the values. Keep essential color keys with the graphic and navigation hints beside their controls. For a comparison matrix, choose meaningful rows and columns, such as methods and models, and put measured results at their intersections.

  Visible incompleteness: Both the mindmap and manuscript should visibly reflect unfinished work. Preserve intended branches, sections, comparisons, table rows and columns, and figures while evidence arrives. Keep empty or explicitly pending result cells, unresolved questions, TODOs, and sentence placeholders beside the relevant argument. Fill entries as evidence becomes available. Preserve verified results and stable TODO identities during reorganization, and expose gaps reopened by scope changes.

  Illustrative comparison matrix, with placeholders for results:

  | Method / Model | Model 1 | Model 2 | Model 3 |
  | --- | --- | --- | --- |
  | Method 1 | [measured result] | | |
  | Method 2 | | [PENDING] | |
  | Method 3 | | | [UNKNOWN] |

  An empty cell keeps an evidence gap open. [PENDING] identifies planned work awaiting execution or a result. [UNKNOWN] identifies an outcome unresolved by the available evidence. A measured zero is recorded as 0 with its metric and supporting evidence. Keep these meanings distinct.

  Sentence placeholder example: "On [DATASET], [METHOD] achieves [RESULT PENDING], measured by [METRIC]."
- Place each TODO beside the passage, claim, theorem, comparison, or result where its outcome will most strengthen the argument. Keep local notes and missing-result markers at the corresponding point of use as the manuscript develops.
- For a long experiment, identify the sentence, figure, or table cell its outcome could change. One paper TODO or placeholder is enough to start. During the run, give the researcher room to experiment. When evidence or a decision changes, draft the smallest update from the run artifact at the same location. A failed run can leave a result pending. Exploratory ideas can stay on draft cards.
- The Primary mindmap covers every stable paper TODO: placed in its tree, or visible in Primary Unplaced. Unplaced counts as coverage.
- Secondary mindmaps may reuse any subset of paper TODOs. The same `todoId` may appear once per map, including on Primary and several secondary maps. Two cards for one `todoId` inside a single map are invalid.
- TeX owns TODO id, text, created/updated/completed. Each map independently owns placement, labels, refs, optional progress, and appearance. Do not persist duplicate TODO text or completion on the map.
- Completing a TODO does not require new manuscript prose.
- Mindmap hierarchy and labels have project-specific meaning. OpenBar assigns none.
- Mindmap nodes may reference stable paper comments. Comment `kind` (claim, question, hypothesis, reviewer, …) is free project vocabulary, not a claim database.
- `\obmarker` is a local paper hole. `\obtodo` is work promoted into the operational maps. Markers do not create mindmap cards.
- Empty or partial tables, planned plots, planned figures, and unresolved marker cells are useful state. Agents preserve row/column axes, fill only available results, leave unresolved cells marked, add axes when scope expands, and make the smallest edit that keeps the unfinished plan.
- Wiki is optional supporting memory, never a second task tracker.
- `AGENTS.md` is core project context. `get_project_state` includes its path and hash by default, and the full body when `detail=full`.
- Project skills are listed, then read by the agent when useful.
- Each mindmap card holds one image. Pasting more images creates child cards. Image width is map-local presentation, stored as `refs[].imageWidth` (25–100 percent). Removing an image detaches it from the card and preserves the shared asset.
- Design a visual card around one readable graphic drawn directly in its body. Give the plot most of the space, crop its SVG viewBox to the marks, and keep labels short. Put the subject in the card title, the takeaway in nearby card text, and methods or detailed explanations in Notes. SVG marks can carry a nested `<title>` for optional values on mouseover. Readers should be able to understand the main result and its uncertainty on touch. Default to OpenBar's violet, blue, pink, orange and amber card accents, selecting only the colors needed and honoring user color preferences. Extract distinct comparisons from a report into child cards as needed. Use actual HTML table elements in an HTML card or a pipe table in Markdown.
- Ordinary cards support `contentFormat: "html"` for compact static HTML and inline SVG visual explanations. Put the plain subject in `title`, HTML source in `text`, and supporting detail in collapsed Notes. `apply_mindmap_edits` add and patch accept `presentation: { contentFormat: "html" }`, including changes to existing cards. HTML body source has a strict 16,384 UTF-16 code unit limit, including markup. Use semantic HTML, SVG `viewBox`, accessible labels, geometry, and fill/stroke colors. OpenBar sanitizes the source to a self-contained static subset and sizes the body to the card width and content height. Paper TODO cards keep TeX formatting. Example: `<svg viewBox="0 0 160 40" role="img" aria-label="Result pending"><rect x="2" y="2" width="156" height="36" rx="8" fill="#ede9fe"/><text x="12" y="26" fill="#5b21b6">Result pending</text></svg>`.
- Every durable field is editable in the human UI and through WebMCP.
- Storage `role=draft` is the Primary map; `role=planning` is a secondary map. The visible product name is OpenBar.
- Card priority uses optional map-local values P0 through P3 and carries no scientific meaning.
- Labels, colors, progress, table layout, refs, and metadata are map-owned presentation fields. TeX remains the source of truth for TODO text and completion.
- Delete stale architecture instead of preserving compatibility branches.
- Keep verification checks temporary and outside the repository. Remove them after use. Keep the repository free of permanent tests.
- Research meaning has no built-in maturity, claim/evidence, or priority workflow.

- Card `title` and `text` are visible. `caption` holds the collapsed Notes. Existing `caution.background`, `caution.critical`, and `caution.important` text appears in the same Notes field, with exact repeated paragraphs combined. Prefer `caption` for new notes. These note fields belong to each map, including on TODO-backed cards. Saved fields remain intact until an explicit Notes edit folds them into `caption`.
- Prefer concise visible cards. Aim for 80 words or fewer of visible card prose. Use `caption` (collapsed Notes) for reasoning, why an answer holds, methods, context, and supporting detail. Keep each research fact in one useful card. Extend an existing relevant card with new detail about the same fact. Use child cards for distinct subtopics or independently useful results. Prefer Agent draft cards for new answers, explanations, and supporting material. Use paper TODOs for research work that belongs in the manuscript. Keep card prose focused on the subject. Let hierarchy, labels, and disclosures communicate organization. Add navigation directions only when they help locate a specific item the reader needs. Keep key findings, consequential risks, and factual uncertainty visible. Card length is a flexible preference, and longer cards are welcome when useful. Agents may use optional length hints returned after a write. Offer card-length advice to people when they ask.
- Agent-created cards and agent-authored content replacements remain marked Agent draft until a human explicitly saves or deletes them. The retired Note shape migrates to Agent draft.
